# Анализ результатов A/B-теста новой формы оплаты ЖКХ (Т-Банк)

**Стек:** `Python` · `pandas` · `NumPy` · `SciPy` · `statsmodels` · `Matplotlib` · `Excel`  
**Методы:** EDA, Data Quality Audit, SRM-тест ($\chi^2$), анализ воронки (Step-to-Step CR), Дельта-метод для ratio-метрик, Z-тест долей, t-критерий Уэлча, критерий Манна–Уитни.

---

## Executive Summary

> **Вердикт: раскатывать новую форму оплаты ЖКХ с автозаполнением реквизитов на 100% пользователей.**

* **Сквозная конверсия платежей (Шаг 1 $\to$ Шаг 4):** выросла с **49.69%** до **64.40%** (**+14.70 п.п.**, относительный прирост **+29.59%**; Дельта-метод: $Z = 7.77, p = 7.77 \times 10^{-15}$).
* **Доля уникальных клиентов с $\ge 1$ успешной оплатой:** выросла с **65.47%** до **80.40%** (**+14.93 п.п.**; Z-тест долей: $Z = 6.51, p = 7.58 \times 10^{-11}$).
* **Число успешных оплат на клиента:** выросло с **0.87** до **1.16** (**+34.1%**; t-критерий Уэлча: $t = 7.06, p = 2.54 \times 10^{-12}$).
* **Guardrail-метрика (время прохождения воронки):** без значимых изменений — **12.43 мин** (A) против **12.35 мин** (B), медиана **12.0 мин** (t-тест $p = 0.60$; Манна–Уитни $p = 0.39$).
* **Устойчивость эффекта:** положительный рост подтверждён на обеих ОС (Android, iOS) и во всех географических сегментах (Москва, СПб, Регионы).

## 1. Контекст и постановка задачи

**Период эксперимента:** 1–30 апреля 2024 года (30 дней).  
**Команда:** продуктовая аналитика, направление платежей.

**Проверяемая гипотеза:**  
Внедрение новой формы оплаты ЖКХ с автозаполнением реквизитов (группа **B**) статистически значимо увеличит сквозную конверсию из открытия формы (Шаг 1) в успешную оплату (Шаг 4) по сравнению со стандартной формой (группа **A**), не замедляя пользовательский путь.

**Дизайн данных:**
* **Единица сплитования:** клиент (`user_id`).
* **Единица анализа воронки:** попытка оплаты (`payment_id`, в среднем 1.77 попытки на клиента).

## 5. Статистическая проверка гипотез

### Обоснование выбора критериев
Поскольку сплитование проводилось по пользователям (`user_id`), а в логах присутствует в среднем 1.77 попытки оплаты на одного клиента, стандартный Z-тест по платежам нарушает предпосылку о независимости наблюдений (внутрикластерная корреляция). Чтобы гарантировать методологическую корректность (при $\alpha = 0.05$, двусторонняя $H_1$), проверка проведена двумя способами:
1. На уровне **платежей** (ratio-метрика) — с помощью **Дельта-метода**, корректирующего дисперсию с учётом кластеризации по клиентам (дополнительно приведён наивный Z-тест для сравнения).
2. На 100% независимом уровне **клиентов** — с помощью **Z-теста долей** и **t-критерия Уэлча** (применим по ЦПТ при $N = 750$ в каждой группе).
3. Для **guardrail-метрики** времени оплаты — **t-критерием** и непараметрическим **критерием Манна–Уитни**.

## 6. Бизнес-рекомендации и следующие шаги

1. **Продуктовое решение (Rollout 100%):** раскатить новую форму с автозаполнением реквизитов на всю аудиторию. Фича даёт двузначный рост конверсии (+14.70 п.п.) и увеличивает частоту успешных транзакций на клиента на +34.1% без деградации времени прохождения сценария.
2. **Точка роста в регионах:** в Регионах прирост конверсии (+10.71 п.п.) заметно ниже, чем в Москве (+18.37 п.п.) и СПб (+14.24 п.п.). Рекомендуется проверить покрытие базы поставщиков и расширить автозаполнение реквизитов для региональных УК и ТСЖ.
3. **Задачи на Data Quality инженерной команде:**
   * исключить тестовые диапазоны (`user_id >= 9001`, `payment_id >= 99001`) из продуктовых витрин;
   * добавить валидацию на `user_id IS NOT NULL` и корректность возраста (14–100 лет);
   * устранить баг перезаписи группы эксперимента в платёжных логах (инцидент с `user_id = 1010`).
